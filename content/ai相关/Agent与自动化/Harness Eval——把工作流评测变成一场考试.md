# Harness Eval——把工作流评测变成一场考试

> **核心命题**：Harness 工作流不是传统软件，不能只靠“感觉更稳了”来迭代，而要建立一套**可重复、可归因、可闭环**的评测系统，让工作流的演进从“主观 vibes”变成“数据驱动改进”。

这篇文章介绍了一套内部使用的 **Harness Eval** 方案：把对工作流的评估，从传统意义上的“测试”升级为“考试”。

## 一、文章在解决什么问题

团队在打磨 Harness 工作流时，最常见的问题不是“做不出来”，而是**做出来之后不知道有没有真的变好**。

典型症状：

- 改了一版 rule / skill，不知道到底是进步还是退步
- A 说好用，B 说不好用，但说不清到底是工作流、模型还是 prompt 的问题
- 修了一个 bad case，可能同时破坏了三个 good case，却没有回归机制发现
- 和竞品相比到底差在哪里，也缺少量化依据

作者的判断很直接：**如果没有评测体系，Harness 工作流实际上就是在“裸奔”。** 你以为系统在进步，实际上可能已经发生了“薛定谔式退化”——变差了，但你不知道。

## 二、为什么不是“测试”，而是“考试”

传统软件更接近确定性系统：

- 同样输入
- 同样输出
- 可以用 `assertEqual` 做二值判断

但 Harness 工作流不是这样。它更像一种 **规则驱动的概率程序**，结果由：

- Prompt
- Rules
- Skills
- Model

共同决定。任何一项微调，都可能引发行为级变化。

因此，问题不只是“对不对”，而是“**好不好**”：

- 是否主动确认关键参数
- 是否在危险操作前做验证
- 是否遇到不确定性会及时汇报
- 是否完成了结果，同时过程也足够稳健

所以作者提出：

- **测试（test）**：验证“对不对”
- **考试（exam）**：评估“好不好”

这篇文章最重要的思维跃迁就是：**我们不是在写测试用例，而是在出考卷、组织考试、培养阅卷官。**

## 三、这套评测系统的三个原则

### 1. 可重复 > 精确

单次跑高分没有意义，多次运行后的结果分布更重要。作者强调追求的是**统计显著的趋势**，而不是一次偶然的满分。

这意味着在 Harness 工作流里，稳定性本身就是质量的一部分。

### 2. 可归因 > 高分

一道题失败后，系统必须告诉你为什么失败。

失败原因至少要区分为三类：

- **[workflow]**：工作流规则、skills、agents 本身有问题
- **[eval]**：题目设计、rubric、环境前提有问题
- **[capability]**：模型或 agent 的通用能力不够

如果只有分数，没有归因，这份评测结果几乎不能指导迭代。

### 3. 闭环 > 单向

评测的终点不是生成成绩单，而是**驱动下一轮改进**。

也就是说，Harness Eval 不是“报告系统”，而是“迭代系统”：

1. 跑评测
2. 找出问题
3. 生成改进建议
4. 喂回工作流
5. 再跑回归

## 四、系统全景：出题 → 答题 → 改卷

整套系统只做三件事：

- **出题**
- **答题**
- **改卷**

但关键在于，它把这三步串成了**无人值守可回归的闭环**。

### 4.1 出题：把题目工程化

每道题由 4 个核心文件构成：

| 文件 | 作用 |
|------|------|
| `meta.yaml` | 题目身份信息：id、版本、类别、难度、考察目标 |
| `task.md` | 题面：给“考生”看的任务描述 |
| `rubric.md` | 阅卷标准：通过项、质量项、典型失分项 |
| `env.yaml` | 环境前提：前置条件、检查命令、关键工件 |

这个设计有几个很强的优点：

- 题目结构标准化，方便扩充题库
- 新出题人不需要理解系统代码，也能快速出题
- `task.md` 与 `rubric.md` 分离，避免“对着标准答案抄”
- 题目可以分层建设：基础层 → 组合层 → 系统层

本质上，这是把“评测题目”变成一种可维护的工程资产。

### 4.2 答题：不是单轮 prompt，而是模拟真实交互

这部分是整篇最关键的设计之一。

最朴素的做法是：直接把 `task.md` 丢给 Agent，然后看最终结果。但作者认为这不符合真实使用场景，因为真实世界里的用户会：

- 补充信息
- 追问
- 纠偏
- 做关键决策

所以他们引入了 **Examiner（考官）** 角色，由 LLM 扮演“用户”，按照剧本和被测 Agent 做多轮对话。

这意味着评测测到的不是“Agent 在单轮任务中的表现”，而是“Agent 在真实交互式工作流中的表现”。

### 4.3 全程录像：结果之外，更看过程

整个答题过程会被记录成 `transcript.jsonl`，包括：

- 每一轮对话
- 每一次 tool call
- 每一条 shell 命令
- 每个执行结果

这非常重要，因为两个 Agent 可能都完成了任务，但质量差异巨大：

- 一个会主动确认关键参数，另一个被追问才补
- 一个先 dry-run 再修改，另一个直接高风险操作
- 一个遇到异常先汇报，另一个擅自替用户做决定

如果只看最终结果，这些差异全部丢失。**Harness Eval 的核心洞察是：Agent 的能力，不只体现在结果，也体现在过程中的决策质量。**

### 4.4 改卷：判卷必须有“上帝视角”

作者踩过一个典型坑：早期让考官顺手打分，结果误判很多。

原因是考官只能看到“对话层”，却看不到真正的行为证据，比如：

- 是否真的写了文件
- 是否真的执行了命令
- 是否真的改了配置

所以他们把 **Judge（裁判）** 做成独立进程，只拿两份材料：

- `rubric.md`
- `transcript.for-judge.txt`

后者不是原始 transcript，而是压缩后的“判卷版”，保留关键行为证据，去掉大量噪音。

裁判阅卷时会做几件事：

1. 逐项核对硬性通过标准
2. 评估过程质量
3. 输出多维度分数
4. 引用 transcript 原文举证
5. 生成分类后的改进建议

这里最关键的是：**每个判定都必须附证据，不允许“我觉得它大概做了”这种推测。**

## 五、评分方式：不止 pass / fail

这套系统不是简单给一个二值结果，而是同时输出：

- `result`：pass / fail
- `compliance`：流程遵循度
- `execution_quality`：执行质量
- `overall`：综合分
- `evidence`：证据引用
- `improvements`：改进建议

这样做的好处是：

- “基本完成但很粗糙”与“完成且过程优秀”不会被混为同一类 pass
- 结果可以画趋势图，观察工作流版本变化
- 改进建议可以直接路由给不同责任人

## 六、执行引擎与工程细节

文章不是停留在理念层，而是讲了不少可复用的工程设计：

### 6.1 Go 写单一 CLI

执行引擎是一个用 Go 写的单一 CLI，追求：

- 零环境部署
- 代码可读性
- 不被重框架绑架

### 6.2 git worktree 隔离

每个并发 run 都在独立 sandbox 中执行，避免不同题目之间互相污染。这个思路和 [[Loop Engineering]] 里强调的 worktree 隔离高度一致。

### 6.3 symlink 替换工作流快照

评测时临时用 symlink 把 IDE 配置目录替换为本轮工作流快照，运行结束后再恢复原配置。这样既能模拟真实环境，又不会污染用户本地设置。

### 6.4 transient 错误自动重试

对 CLI 崩溃、网络抖动等瞬时错误进行有限重试，但对超时不盲目重试。这个细节说明作者区分了“偶发失败”和“系统性失败”。

### 6.5 workflow_rev 记录 commit

每次 run 都记录所用工作流的 git commit，这样当通过率从 0.8 下降到 0.6 时，可以直接回溯到对应改动，而不是靠记忆猜。

## 七、最终效果

文章给出的实际结果是：

- 对团队内部 Harness 工作流做了 **4 轮 `workflow_rev` 迭代**
- 累计跑了 **50+ 次自动化 run**
- 通过率从 **82.4%（14/17）提升到 100%（17/17）**

同时系统性暴露并修复了这些问题：

- 范围锁定
- Critical 拦截
- 归档沉淀
- 提交规范
- TDD 纪律

也就是说，这套系统不是“评测完就结束”，而是真的推动了工作流设计向前演进。

## 八、这篇文章最值得吸收的启发

### 1. Harness 工作流需要的是评测工程，不是体感优化

如果不能回答“上一版和当前版谁更好”，那所谓的持续改进大概率只是自我感动。

### 2. 评测不该只看结果，而要看行为过程

很多高质量与低质量 Agent，在最终结果上看起来都能“完成任务”，但它们的风险轮廓完全不同。真正可用的评测必须覆盖过程。

### 3. maker-checker 分离非常关键

执行的人不能同时是判定自己是否做得好的那个人。这个思想与 [[Claude Code Dynamic Workflows 动态工作流]]、[[Loop Engineering]] 中的多 agent 分工逻辑高度一致。

### 4. 评测系统的最终目标是驱动迭代

最好的评测不是“告诉你多少分”，而是“告诉你下一步改什么、为什么改、该谁改”。

## 十、我自己的提炼

如果把全文压缩成一句话：

> **给一个行为不确定的 Harness 工作流，建立一套可重复、可归因、可闭环的质量度量体系。**

这篇文章真正有价值的地方，不只是介绍了一个内部系统，而是提供了一个判断标准：

- 没有量化，就没有优化
- 没有归因，就没有迭代
- 没有闭环，就没有工程化

对于任何开始把 Agent 放进生产工作流的人来说，这篇文章都在回答同一个问题：**当 Agent 不再是玩具，而是关键路径里的执行者时，你如何知道它到底是不是在变好？**
