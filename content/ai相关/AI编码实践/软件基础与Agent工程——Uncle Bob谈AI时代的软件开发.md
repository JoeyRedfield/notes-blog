# 软件基础与 Agent 工程——Uncle Bob 谈 AI 时代的软件开发

> [!abstract] 本页定位
> 这是一场 Matt Pocock 与 Robert C. Martin（Uncle Bob）的访谈整理。它不是对逐字稿的翻译，而是提炼其中关于 Agent 工作流、自动化质量门、模块设计、规划方式和程序员培养的可复用观点。

## 一句话结论

**AI 吃掉的是战术性编码，不是战略性软件工程；软件基础仍然是把复杂性组织成可理解、可验证结构的办法，只是越来越多的实现劳动可以交给 Agent。**

Uncle Bob 的实践目标不是“永远不碰代码”，而是让 Agent 在一套足够强的确定性约束中工作，把人的注意力转移到：

- 目标是否正确，模块和接口是否合理；
- 测试、架构规则和验收流程是否能自动发现错误；
- Agent 是否陷入反复修改、破坏—修复的循环。

## 1. 为什么坏代码会让 Agent 失速

Uncle Bob 早期使用 Agent 时发现：它们虽然生成得快，却会留下大量混乱。若继续在混乱之上追加功能，Agent 会逐渐出现以下行为：

1. 修改一个地方时意外破坏另一个地方；
2. 不断修复新问题，又引入下一个问题；
3. 在上下文中打转，最后无法继续工作。

这说明 Agent 和人一样会受到混乱代码的影响。速度不能抵消结构性复杂度，反而会更快地把代码推入 Agent 无法处理的区域。因此，**代码质量不是审美问题，而是 Agent 能否持续工作的前置条件**。

## 2. 用确定性工具代替长篇规训

Uncle Bob 一开始也尝试在提示词里塞入 TDD、Clean Code 和各种编码规则，但发现模型会把这些规则当作“指南”，而不是硬约束。上下文越来越长时，还会受到 **Lost in the Middle** 的影响：开头和结尾的信息更容易被保留，中间的长篇规则逐渐失去作用。

他的做法是：

- 把初始提示词压缩到绝对必要的最小集合；
- 把必须遵守的要求交给类型系统、测试、静态分析、架构检查、CRAP 分析、Mutation Testing 和 UI/系统测试；
- 让 Agent 进入“修改代码，直到工具通过”的反馈循环。

这类工具不会因为上下文窗口变长而“被遗忘”。不过，约束也不能无限叠加：校验成本过高会把 Agent 拖慢到不如人，工程上需要在质量和吞吐量之间寻找阈值。

## 3. Uncle Bob 的 Agent 质量流水线

他描述了一条由多个短生命周期 Agent 组成的流水线。每个 Agent 聚焦单一职责，完成后把结果交给下一个 Agent，必要时可以并行运行多个编码任务。

| 阶段 | 主要输入 | 主要工作 | 输出或门槛 |
| --- | --- | --- | --- |
| Specifier | 人写的故事或需求 | 转成 Gherkin（Given/When/Then）验收场景和面向用户的 QA 流程 | 可执行的行为描述 |
| Coder | 故事、Gherkin、QA 文档 | 编写单元测试和实现代码，让故事与验收测试通过 | 初步可运行的功能 |
| Cleaner | Coder 的改动 | 运行 CRAP 分析并进行一般性代码清理 | 更低的复杂度和更整洁的结构 |
| Hardener | 清理后的代码 | 运行 Mutation Testing，杀死存活 mutant，补齐测试缺口 | 更强的测试有效性 |
| QA Agent | QA 流程 | 把人工操作步骤变成可执行的系统测试并检查确定性结果 | UI/系统层面的验收 |

Uncle Bob 的经验是：一个 Agent 五分钟能勉强完成的任务，经过这条约一小时的流水线后，通常仍比人类半天的工作快，而且质量门更密集。代价是 Agent 启动、交接和通信存在开销；收益是每个上下文更短、角色更清楚，也更容易在某个阶段定位问题。

### 多 Agent 的两个主要收益

- **并行**：多个编码任务可以同时推进。
- **隔离上下文**：Agent “出生、完成任务、退出”，下一个 Agent 以干净上下文开始，降低轨迹污染和 Lost in the Middle 的影响。

相应的代价是启动时间、上下文重新加载和 Agent 之间的沟通成本。多 Agent 不是越多越好，重点是职责边界是否真的降低了复杂度。

## 4. 模块设计是 Agent 的认知支架

Uncle Bob 与 Matt 都把 John Ousterhout 的 **Deep Modules（深度模块）** 视为 AI 时代仍然有效的设计原则：用小而清晰的接口隐藏大量实现细节。Agent 能先通过接口、命名和测试理解模块的职责，而不必一开始读完内部所有代码。

Uncle Bob 的实践包括：

- 用架构查看器展示模块、子模块和依赖关系，并支持逐层钻取；
- 用单独的依赖规则文件规定哪些模块可以依赖哪些模块；
- 在流水线末尾检查规则，违规时要求 Agent 反转依赖、插入接口或拆分模块；
- 把一个模块限制在相对一致的主题内，避免“咖啡问题和肥皂剧混进同一个上下文”的轨迹污染。

核心逻辑是：**良好的模块边界同时服务于人和模型，因为两者都需要把复杂系统分割成可管理的概念单元。**

## 5. 不要机械复制人的开发纪律

Uncle Bob 对“软件原则”和“人的工作纪律”做了区分：

- **价值可以保留**：低复杂度、可测试、清晰接口、持续验证等目标仍然重要。
- **行为可以调整**：不要把针对人类短期记忆设计的每一步流程，原封不动地强加给 Agent。

例如，TDD 对人类很有帮助，因为人类需要用极小的红—绿步长控制认知负荷。但他不认为 Agent 必须严格做到“写一行测试、写一行生产代码、再写一行测试”。在实践中，他允许 Agent 先完成一个函数，再为其补测试，只要最终质量门、覆盖率和行为验证达标。

他还在实验不同的 CRAP 阈值：人类代码可能要求低于 4，Agent 可以先放宽到 6，甚至尝试 8。这里的分数同时受测试覆盖率和圈复杂度影响，不能把某个数字当作普适真理；关键是用实证找到 Agent 在项目中的可承受阈值。

> [!warning] 不要把 Agent 的辩论当作证据
> Agent 可以参与讨论阈值和架构，但它给出的理由本身不能替代测试、静态检查和真实反馈。

## 6. 规划：小步反馈胜过计划堆叠

Uncle Bob 对“先把规格写到极致，再一次性交给 Agent”的做法持怀疑态度。他的实验显示，计划可以写得非常漂亮，但执行时仍会因为遗漏前提或错误假设而崩溃，最后只能停下来重写计划。

他倾向于重新借鉴敏捷方法：

1. 先做一两个故事；
2. 观察结果和架构；
3. 人工整理必要的模块边界；
4. 再做下一批故事并重复反馈。

这里的关键不是拒绝所有前置对齐，而是拒绝把前置文档误认为最终真相。访谈中他把规格称为 **ephemeral（临时的、会消失的）**：规格会随着探索不断修改，最终可运行的结果、测试和约束才是更可靠的“规格”。这也解释了他为什么更愿意让 Agent 参考已有工具的实现，再为当前项目构建定制版本，而不是直接下载一套自称通用的工具。

## 7. 战略编程与程序员培养

访谈用 John Ousterhout 的区分收束了人的角色：

- **战术编程**：实现一个具体任务、修一个局部问题，Agent 已经非常擅长；
- **战略编程**：决定系统边界、模块结构、依赖方向、反馈机制和长期演进路线，仍需要人的判断。

Uncle Bob 给初学者的建议不是跳过代码直接学习提示词，而是经历一条由底到顶的路径：

1. 先实际写代码一段时间，理解 Agent 正在操作的对象；
2. 从二进制、汇编、C 等基础逐步上升到 Python 等高层语言；
3. 在使用 Agent 的团队里，先像 Agent 一样接受具体任务和确定性质量门；
4. 经历几个月的低效率训练，学会识别 Agent 何时开始“挣扎”和循环；
5. 最后再承担监督和战略编排 Agent 的职责。

他推荐重新阅读 Tom DeMarco、Ed Yourdon、《The Pragmatic Programmer》等经典著作，并承认需要过滤其中已经过时的技术背景。战略判断往往来自对失败模式的体感：如果没有亲自经历过混乱、返工和系统性失速，就很难及时识别 Agent 正在重演这些问题。
