# AI 原生工程团队运作实践

> 来源：Fiona Fung（Anthropic Claude Code 工程总监）在 AI Engineer 大会的演讲，分享 Claude Code 团队在 Agentic Coding 成为默认工作方式后，流程、规范和团队结构发生的根本变化。

## 核心论点：瓶颈转移了

**过去**，工程带宽（coding throughput）是软件开发中最昂贵的部分。所有流程——从瀑布到敏捷——都围绕这个成本设计。写代码、写测试、重构，这些曾经需要专门排期的"重活"，现在不再是瓶颈。

**现在**，在 Claude Code 团队，编码很少再是慢的环节。但瓶颈没有消失——它们转移到了：

- **验证（Verification）**：代码是否正确？
- **代码审查（Code Review）**：人类如何跟上 AI 生成的代码量？
- **安全（Security）**：信任边界和敏感代码的审查
- **维护（Maintenance）**：生成大量代码后，维护成本怎么控制？

> 核心洞察：曾经服务于你的流程，现在可能不再适用。但流程很少会自我消亡——它们只会越叠越多。

## 四大新规范

### 1. 规划：从六个月路线图到 JIT（Just-in-Time）

**旧做法**：花大量时间预先规划，因为编码时间昂贵。

**新做法**：Fiona 加入 Claude Code 团队时写了一份六个月的路线图，三个月后就过时了。现在采用 JIT 规划——类似 JIT 编译，在合适的时间做刚好够的规划：

- 设计文档 → **PR 或原型即讨论**，"doc 不如 PR"
- 产品评审 → **原型 + 内部用户 + 反馈迭代**
- 因为原型成本极低，先做出来让用户用，比先写文档再评审高效得多

**技术争论的新解法**：代码比争论便宜。Fiona 和 Boris（Claude Code 技术负责人）有一次技术分歧，她不再拉人去白板争论，而是直接生成三个不同实现的 PR，不仅比较实现方式，还能看到每种方案对调用者的实际影响。

> ⚠️ 但这要求更强的团队文化——不能变成"最后提交的人获胜"。需要开放、诚实的技术讨论和团队对齐。

### 2. 上下文获取：先问 Claude，不是先问作者

**旧做法**：找到写这段代码的人问。

**新做法**：因为所有 PR 都有 Claude 参与，"谁写的"不再是最有用的问题。改为"双击"追问——你真正想回答的问题是什么？

- 查找回归原因？→ 让 Claude 分析变更历史和上下文
- 需要专家回答客户问题？→ Claude + 代码库可以直接回答
- 了解某个决策背景？→ 让 Claude 搜索相关 PR 和讨论

更进一步：**"这个问题能不能自动化？"** Fiona 每天早上的例行工作是打开客户反馈频道让 Claude 总结——现在这已经变成了 Claude Routines 自动运行的后台任务。

### 3. 代码审查：Trust but Verify

这是 Fiona 被问最多的问题："人类如何跟上代码审查？"

Claude Code 团队使用 [Claude Code Review](https://code.claude.com/docs/en/code-review) 处理所有风格检查、lint、PR 反馈请求、bug 发现与修复、测试添加。

**Claude 负责**：风格、lint、常见 bug、测试生成、PR 反馈

**人类仍然必须参与**：
- 法律审查（风险容忍度）
- 信任边界和安全敏感代码（拉领域专家）
- 产品感知和品味（PM/设计师审查用户体验）

> 关键是持续评估 trust 和 verify 的边界——这个边界会随着模型能力提升不断移动。今天需要人类的地方，下一个模型可能就不需要了。

### 4. 团队构成：角色模糊化

AI 模糊了传统角色的边界：

- **PM 现在写很多代码**——这很有趣
- **工程师可以承担内容和设计工作**——传统上不属于技术侧
- **非传统程序员能做更多工程工作**——Claude 补齐了编码短板

**Fiona 重点招聘两类人**：

| 类型 | 特征 | 为什么重要 |
|------|------|-----------|
| **创意构建者 + 产品感** | 梦想家、好奇心强、热衷于用产品解决问题、通过迭代打磨体验 | AI 处理吞吐量，人类提供方向和品味 |
| **深层系统专长** | 分布式系统、底层基础设施 | 构建 Claude Code on the Web 等需要"到处运行 Claude"的场景 |

**不再作为重点的能力**：原始编码吞吐量——模型已经解决了这个问题。

## 落地策略：强制 vs 自治的平衡

### 不可协商的团队原则

- **无情地 Dogfood 自己的产品**：每个团队成员（包括跨职能伙伴）都使用 Claude Code 和 Claude Cowork
- **尽量扁平化**：管理者从 IC 做起，先通过实际交付学习如何成为有效工程师，赢得团队信任。一个整体团队使命，管理者支持工作 Pod 但保持敏捷
- **显式授权消灭旧流程**：定期问"这还有用吗？"团队有明确的权限质疑和终止不再有效的流程

### 留给 Pod 的自治空间

在几条原则之内，每个 Pod 有很大自主权：如何用 Claude 做 triage、如何运行站会（Fiona 团队从传统站会 → 电子表格 → Claude Standup Skill，持续演进）、哪些工作流先"Claudify"。

## 衡量指标：如何知道新规范在生效

| 指标 | 方向 | 说明 |
|------|------|------|
| 入职 ramp-up 时间 | ↓ 下降 | 工程师/设计师/PM 多快能开始有效产出。Claude Code 团队现在新人在第一周就能交付真实代码 |
| PR 周期时间 | ↓ 下降 | 不仅能看 AI 采用情况，还能发现流水线瓶颈——代码生成多了，构建系统和 CI 可能跟不上 |
| Claude 辅助提交占比 | ↑ 上升 | Claude Code 团队默认每个提交都是 Claude 辅助的，Fiona 说近四个月没见过非 Claude 辅助的提交 |

> 不要混淆吞吐量和成功。吞吐量是一个指标，但真正的指标是你要解决的问题有没有被更好地解决。质量、可靠性同样需要关注。

## 个人关联与实践建议

这篇文章与当前工作模式高度相关：

1. **已经在实践"先问 Claude"**——这是正确的方向。进一步思考哪些重复性操作可以自动化（Routines、脚本）。
2. **代码审查的 trust-but-verify 框架**——在用 Claude 辅助写代码时，保持对关键逻辑的人工审查是必要的，尤其是在安全、事务边界、数据一致性等场景。
3. **JIT 规划思维**——面对复杂业务需求时，可能不需要长篇设计文档，而是快速原型 + 用户反馈迭代。
4. **"杀旧流程"的心态**——进入新团队后，先理解现有流程，再分辨哪些是真正有效的、哪些只是惯性。
5. **关注的指标**——Claude 辅助提交占比可以很高，但要关注 PR 质量而非数量。

> [!note]- 延伸阅读：团队招聘与组织结构细节
>
> ### 组织形状：极度扁平
>
> Fiona 加入时，招聘团队还在用传统的"10 个 IC 对 1 个管理者"配比。她坚持所有管理者必须先从 IC 做起，先交付代码赢得信任。原因很简单：**无法再忍受不碰代码的管理者**——过去在 Meta 她每年还试图交一个 PR，但内部工具和工作流变化太快。现在有了 Claude，不需要记 git 命令，管理者也能持续参与编码。
>
> 招聘团队当时担心"没有管理者会接受从 IC 开始"，Fiona 的回答是："这就是 Claude Code 团队的 Dogfooding。如果有人不接受，那就是早期分离，对双方都好。"
>
> ### 团队知识的来源
>
> 在 Claude Code 团队，**代码即真相来源**。回答客户问题时直接查代码库，避免了文档与代码不同步的老问题。如果团队有高质量 spec，可以将其检入仓库，让 Claude 对照 spec 验证代码执行。
>
> ### Fiona 仍在问自己的问题
>
> - **iOS/Android 组织**：当工程师可以高效跨平台开发时，传统的 iOS 团队 + Android 团队拆分还有意义吗？
> - **全自动审查的边界**：在"够快"和"丢失重要信息"之间如何平衡？下一版模型可能会改变这个平衡。
> - **角色模糊后的公平感**：如何确保每个人在角色边界模糊后仍然感到公平的生产力认可？
>
> ### 立即行动：选一个最"吵"的工作流
>
> Fiona 讲了一个故事：她曾在某个团队参加一个每周大审，50 人在会议室里，每个人都在看笔记本，只有轮到自己的时候抬头报一下状态，然后继续低头。她问了一个问题："**我们为什么开这个会？**"所有人恍然大悟，会议被取消了。
>
> 挑一个团队最吵、最贵、或你最不想做的工作流，问：它还在服务最初设立它的目的吗？如果能，能否自动化？
