# 把一本书做成 AI Skill 方法论

> 源作者：[@AYi_AInotes](https://x.com/AYi_AInotes)，2026-06-01 发布

## 核心理念

**读过，不等于用得上。** 大多数人读书只是在囤积信息，没有做到知识的调用。把一本书做成 AI skill，不是做摘要或读后感，而是把书里的框架、原则、技法、反模式变成 AI 能照着执行的指令——让知识真正能被随时"喊出来用"。

## 为什么这件事需要顶级模型

把书做成 skill 的真正难点不在提炼，而在于让 AI **读全**。一本书几万字，必须让 AI 把整本逻辑链一次吃进去——一旦被切碎，跨章节的因果就断了，提炼出来的框架基本是残的。

Claude Opus 4.8（100 万 token 上下文）的三个能力刚好卡这个任务：
- **长上下文**：整本书一次读完，不切块、不丢逻辑
- **结构化输出**：直接吐出规整的 skill 文件
- **多步 agentic**：生成完自己做自检和试调用，发现空洞回去补

## 六步操作流程

### 第一步：把书变成纯文字

拿到整本书干净的纯文本（.txt 或 .md），图表排版丢了没关系，文字逻辑在就行。

三种情况：
- **Word/网页**：另存为 .txt，或全选复制粘贴
- **PDF/EPUB**：用 Calibre（免费，[calibre-ebook.com](https://calibre-ebook.com)）转换为 TXT
- **在线工具**：搜 "epub 转 txt 在线"，但注意别用要付费的

> 关键：要整本干净文字，别先让任何工具帮你摘要再喂——摘要会把框架精度丢光。

### 第二步：喂给模型，先别让它摘要

上传 .txt 或分段粘贴全文，发这段 prompt：

```
这是《[书名]》全文。先不要摘要。
通读全书，给我一张全局结构地图：
核心论点是什么？围绕它有哪些命名框架/原则/技法/反模式？它们之间什么逻辑关系？
作者的语气有什么辨识度？
我想用它做一个能帮我 [你的目的] 的 skill。
```

### 第三步：按五类提炼，做台账

```
按这 5 类提炼这本书：框架 / 原则 / 技法 / 反模式 / 作者声音。
每条给：名字 + 一句话定义 + 何时用 + 原书的精确表述。
框架要保留作者的原始命名，别改写成通用说法。
哪些是核心必进、哪些是边角可省？给我一张台账表格。
```

### 第四步：生成 skill

先判断规模：框架少（1-3 个）做成一个文件；框架多（10+）做成「入口文件 + 分文件懒加载」。

```
按这份台账生成一个 Cursor skill。
重点打磨开头那段 description——
把「用户会在什么场景、说什么话时需要它」全写进去，
因为这决定它会不会被 AI 自动召回，写不好等于白做。
```

**这一步的关键**：description 里的触发词决定了 skill 能不能在你需要时被自动召回。要写具体的场景和口语化表达，而非正式书名。

### 第五步：自检 + 试调用（最容易被跳过但不能省）

**① 召回测试**：

```
只看这个 skill 开头的 description，
用户说这 5 句话时你会不会想起调用它？逐句判断。
```

**② 调用测试**：

```
现在真用这个 skill 完成一个任务：[一个这本书能解决的真实问题]
看你给的是能照做的步骤，还是空话。
```

发现问题就回第四步补。这一步不做等于白做——作者第一版触发词写窄了，只有说正式书名才召回，补上日常表达后才真正可用。

### 第六步（可选）：多模型 PK

同一份台账丢给不同模型各生成一版，对比谁提炼得更准、触发词更全。

## 案例复盘：《非暴力沟通》

- **选书原因**：框架清晰（四要素 OFNR、长颈鹿语言 vs 豺狗语言、疏离生命的语言），适合做 skill
- **全程时间**：首次 45 分钟（含配置），熟悉后约 20 分钟
- **实际成本**：约 30 万 token，折合不到 ¥20
- **生成效果**：Opus 4.8 保留了书里原始命名，把"要好好说话"变成了可执行的四步：观察 → 感受 → 需要 → 请求
- **自检发现**：第一版触发词太窄（只说"非暴力沟通"才召回），补充了"怎么提意见不像在指责""和家里人又吵起来了怎么办"等日常表达后才真正可用
- **真实体验**：作者和家人的一次沟通中直接调用 skill，用 OFNR 四步把想说的话拆开重排，去掉了"你总是""你又"的指责性表达

## 关键启示

1. **书变成 skill 后才是真正的知识激活**：读过和能用之间差了一整个 skill
2. **触发词决定可用性**：description 要写用户**真实会说的话**，不是正式书名
3. **自检不能省**：不测试召回率等于白做
4. **成本很低**：一本中等体量的书，全程不到 ¥20
5. **护城河在转移**：从"读过多少书"变成"把多少书变成了随时调得动的产能"

## 个人讨论：Skill 的必要性边界

> 以下为 2026-06-02 摄入后讨论的总结。

### 一个重要区分：什么时候真的需要 skill

表面上适合做 skill 的场景，仔细一想大多数**不需要 skill 也能做到**。Claude Code 本身就能读项目代码、查知识库、按指令执行任务。很多看似合理的 skill 场景，只是给已有能力加了一层仪式感，核心价值增量很小。

skill 真正不可替代的场景有三个特征：

1. **触发时机不可预测**——你不会专门打开 Claude Code 去用它，而是在某个随机时刻突然需要
2. **方法论固定且可操作**——不是泛泛的建议，而是确定性的步骤/框架/流程
3. **跨会话随时可用**——不在特定项目上下文里，但在任何对话中都能被召回

《非暴力沟通》skill 之所以有价值，是因为它同时满足了这三个条件：你不会计划着"今天要好好沟通"，而是吵架了才想起来；OFNR 四步是确定的流程；沟通场景可能出现在任何时候。

### 在当前个人场景下的判断

尝试映射到自身场景（Java 后端入职准备 + AI 应用开发）：

- **Java 面试题**：Claude Code 直接出题追问即可，不需要 skill
- **制造业术语速查**：库里已有笔记，直接查即可
- **代码模板生成**：Claude Code 能读项目代码按风格生成，不需要 skill
- **STAR 项目故事拆解**：有一定重复性，但触发频率不够高，暂不需要
- **代码 review 自检清单**：入职后可能需要，目前为时过早

**结论**：当前阶段没有明确的 skill 制作需求。但这套方法论本身值得保留——当未来真的遇到"每次都要解释一遍上下文、且触发时机不可预测"的痛点时，再回来用它。
