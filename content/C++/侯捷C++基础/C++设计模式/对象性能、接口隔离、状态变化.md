# 对象性能

面向对象很好地解决了“"抽象”的问题，但是必不可免地要付出一定的代价。对于通常情况来讲，面向对象的成本大都可以忽略不计。但是某些情况，面向对象所带来的成本必须谨慎处理. 

## Singleton

### 动机

- 在软件系统中，经常有这样一些特殊的类，必须保证它们在系统中只存在一个实例，才能确保它们的逻辑正确性、以及良好的效率。
- 如何绕过常规的构造器，提供一种机制来保证一个类只有一个实例？
- 这应该是类设计者的责任而不是使用者的责任。

### 模式定义

> 保证一个类仅有一个实例, 并提供一个该实例的全局访问点. ——《设计模式》GOF

### 结构

![[Untitled 891.png]]

```c++
// 这里是伪代码, 方便对照着各种实现方式看
#include <atomic>
#include <mutex>
class Singleton {
private:
    Singleton();
    Singleton(const Singleton& other);
    static Singleton* m_instance; //下面的m_instance是给懒汉模式用的.
    static std::atomic<Singleton*> m_instance; // 静态成员变量，存储唯一实例的指针
    static std::mutex m_mutex; // 互斥锁，用于保护实例的创建过程
public:
    static Singleton* getInstance();
};
Singleton* Singleton::m_instance = nullptr;

//线程非安全版本
Singleton* Singleton::getInstance() {
    if (m_instance == nullptr) {
        // 2个及以上的线程的话，有概率会执行2次new Singleton
        m_instance = new Singleton();
    }
    return m_instance;
}


//线程安全版本，但锁的代价过高
//高是因为这么设计的话，每次getInstance都要获取锁
Singleton* Singleton::getInstance() {
    Lock lock; // 这里相当于获取了锁
    if (m_instance == nullptr) {
        m_instance = new Singleton();
    }
    return m_instance;
}

// 双检查锁，但由于内存读写会出现reorder不安全
// 正常流程是分配内存，调用构造器初始化Singleton，把指针返回值给m_instance。
// 在CPU指令级别，可能会出现指令reorder：可能分配内存后直接给了m_instance，最后再调用构造器。
Singleton* Singleton::getInstance() {
    // 先问是否为空，再加锁
    // 里面的if检查是必要的，不然加锁就没意义了->回到了线程非安全版本
    if (m_instance == nullptr) {
        Lock lock;
        if (m_instance == nullptr) {
            m_instance = new Singleton();
        }
    }
    return m_instance;
}

//上面的（指令级）问题是编译器需要解决的。
//C++ 11版本之后的跨平台实现 (volatile)
// 这是一个懒汉式单例模式的实现，它在需要的时候才创建实例。
std::atomic<Singleton*> Singleton::m_instance = nullptr;
std::mutex Singleton::m_mutex;

// 获取单例实例的方法实现
Singleton* Singleton::getInstance() {
    // 使用原子操作读取m_instance指针，并且使用std::memory_order_relaxed屏蔽编译器的reorder优化
    Singleton* tmp = m_instance.load(std::memory_order_relaxed);

    // 获取内存fence（屏障/保护），确保读取m_instance指针的操作先于后续对对象的访问
    std::atomic_thread_fence(std::memory_order_acquire);

    // 第一次检查：如果实例指针为空，表示还未创建实例
    if (tmp == nullptr) {
        // 使用互斥锁保护下面的操作，确保只有一个线程能够创建实例
        std::lock_guard<std::mutex> lock(m_mutex);

        // 重新检查实例指针，因为在等待锁期间其他线程可能已经创建了实例
        tmp = m_instance.load(std::memory_order_relaxed);

        // 第二次检查：如果实例仍然为空，表示确实未创建实例
        if (tmp == nullptr) {
            // 创建新的实例
            tmp = new Singleton;

            // 释放内存fence，确保对象创建先于对m_instance指针的写入操作
            std::atomic_thread_fence(std::memory_order_release);

            // 将实例指针存储到m_instance，使用std::memory_order_relaxed屏蔽编译器的reorder优化
            m_instance.store(tmp, std::memory_order_relaxed);
        }
    }

    // 返回实例指针
    return tmp;
}
```

### 要点总结

- Singleton模式中的实例构造器可以设置为protected以允许子类派生。
- Singleton模式一般不要支持拷贝构造函数和Clone接口，因为这有可能导致多个对象实例，与Singleton模式的初衷违背。
- 如何实现多线程环境下安全的Singleton? 注意对双检查锁的正确实现。

## Flyweight

### 动机

- 在软件系统采用纯粹对象方案的问题在于大量细粒度的对象会很快充斥在系统中，从而带来很高的运行时代价——主要指内存需求方面的代价。
- 如何在避免大量细粒度对象问题的同时，让外部客户程序仍然能够透明地使用面向对象的方式来进行操作？

### 模式定义

> 运用**共享**技术有效地支持大量细粒度的对象. ——《设计模式》GOF

### 结构

![[Untitled 892.png]]

cache可以理解成一个对象池, 存在就返回, 不存在就创建, 体现了共享思想. 

### 应用场景

设计一个字体(Font)类, 每一个字符(string key)都有一个字体. 还需要一个FontFactory, 其内有map类模拟fontPool, 使用者通过GetFont(const string)方法获取font. 

```c++
class Font
{
private:
	string s;
public:
	Font(const string& key){
		s = key;
	}
	string& getWord() {
		return s;
	}
};

class FontFactory
{
private:
	map<string, Font*> fontPool;
public:
	Font* getFont(const string& key) {
		map<string, Font*>::iterator it = fontPool.find(key);
		if (it == fontPool.end()) {
			fontPool[key] = new Font(key);
		}
		return fontPool[key];
	}
};
```

```c++
int main() {
	FontFactory fontFactory;
	Font* font1 = fontFactory.getFont("Arial");
	cout << font1->getWord() << endl;
}
```

### 要点总结

- 面向对象很好地解决了抽象性的问题，但是作为一个运行在机器中的程序实体，我们需要考虑对象的代价问题。Flyweight主要解决面问对象的代价问题，一般不触及面向对象的抽象性问题。
- Flyweight**采用对象共享的做法来降低系统中对象的个数，从而降低细粒度对象给系统带来的内存压力**。在具体实现方面，要注意对象**状态**的处理。一般来说需要只读. 
- 对象的数量太大从而导致对象内存开销加大，什么样的数量才算大？这需要我们仔细的根据具体应用情况进行评估，而不能凭空臆断。

# 接口隔离

在组件构建过程中，某些接口之间直接的依赖常常会带来很多问题、甚至根本无法实现。采用**添加一层间接（稳定）接口**，来隔离本来互相紧密关联的接口是一种常见的解决方案。

## Facade

### 动机

![[Untitled 893.png]]

- 上述A方案的问题在于组件的客户和组件中各种复杂的子系统有了过多的耦合，随着外部客户程序和各子系统的演化，这种过多的耦合面临很多变化的挑战。
- 如何简化外部客户程序和系统间的交互接口？如何将外部客户程序的演化和内部子系统的变化之间的依赖相互解耦？

### 模式定义

> 为子系统中的一组接口提供一个**一致（稳定）**的界面, cade模式定义高层接口，这个接口使得这一子系统更加容易使用(复用). ——《设计模式》GoF

简单来说还是抽一层出来. 

### 结构

![[Untitled 894.png]]

### 应用场景

这个模式更加体现在设计素养, 设计思想. 比如前后端交互都可以说成是门面模式: 前端调用一个后端接口, 后端可能需要做很多工作, 即使后端怎样修改代码, 对外暴露的接口的使用方式一般都是不变的.  

### 要点总结

- 从客户程序的角度来看，Facade模式简化了整个组件系统的接口, 对于组件内部与外部客户程序来说，达到了一种“解耦”的效果——内部子系统的任何变化不会影响到Facade接口的变化。
- Facade设计模式更注重**从架构的层次**去看整个系统，而不是单个类的层次。Facade很多时候更是一种架构设计模武。
- Facade设计模式并非一个集装箱，可以任意地放进任何多个对象。Facade模式中组件的内部应该是“相互耦合关系比较大的一系列组件”, 而不是一个简单的功能集合。

## Proxy

### 动机

- 在面向对象系统中，有些对象由于某种原因 (比如对象创建的开销很大，或者某些操作需要安全控制，或者需要进程外的访问等) 直接访问会给使用者、或者系统结构带来很多麻烦。
- 如何在不失去**透明操作**对象的同时来管理/控制这些对象特有的复杂性？增加一层间接层是软件开发中常见的解决方式。

### 模式定义

> 为其他对象提供一种代理以控制（隔离，使用接口）对这个对象的访问。——《设计模式》GoF

### 结构

![[Untitled 895.png]]

### 应用场景

Proxy模式在实际实现上会比较复杂, 偶尔会要用工具去生成. 老师没有讲案例, 所以去[电子书网站](https://refactoringguru.cn/design-patterns/proxy)看了一下, 但是它用的不是C++代码, 所以我根据类图尽量复现了代码. 

程序库提供了视频下载类。 但是该类的效率非常低。 如果客户端程序多次请求同一视频， 程序库会反复下载该视频， 而不会将首次下载的文件缓存下来复用。

代理类实现和原下载器相同的接口， 并将所有工作委派给原下载器。 不过， 代理类会保存所有的文件下载记录， 如果程序多次请求同一文件， 它会返回缓存的文件。

![[Untitled 896.png]]

```c++
#include <iostream>
using namespace std;
// 这里只是简单模拟了下载一个文件的情况
class ThirdPartyTVLib
{
public:
	virtual void listVideos() = 0;
	virtual void getVideoInfo(int id) = 0;
	virtual void downloadVideo(int id) = 0;
};

class ThirdPartyTVClass : public ThirdPartyTVLib
{
private: 
	bool flag = false;
public:
	virtual void listVideos() {
		cout << "ThridParty list videos" << endl;
	}
	virtual void getVideoInfo(int id) {
		cout << "third get info " << id << endl;
	}
	virtual void downloadVideo(int id) {
		// 模拟下载
		if (!flag) {
			flag = true;
			cout << "start downloading " << id << endl;
		}
		else {
			cout << "already downloading " << id << endl;
		}
	}

};

class CachedTVClass : public ThirdPartyTVLib
{
private:
	ThirdPartyTVLib* service = nullptr;
public:
	// 这里保证了必须添加ThirdPartyTVLib原下载器，所以后面不需要再检查是否为空了
	CachedTVClass(ThirdPartyTVLib* s) : service(s) {}

	virtual void listVideos() {
		cout << "cached list videos" << endl;
		// 委派给原下载器
		service->listVideos();
	}
	virtual void getVideoInfo(int id) {
		cout << "cached videoinfo" << id << endl;
		service->getVideoInfo(id);
	}
	virtual void downloadVideo(int id) {
		service->downloadVideo(id);
		cout << "cached downloading " << id << endl;
	}
};
```

```c++
int main() {
    ThirdPartyTVLib* startDownload = new ThirdPartyTVClass();
    ThirdPartyTVLib* proxy = new CachedTVClass(startDownload);

    proxy->listVideos();
    proxy->getVideoInfo(1);

    // start downloading 1
    // cached downloading 1
    proxy->downloadVideo(1);

    // already downloading 1
    // cached downloading 1
    proxy->downloadVideo(1);

    delete proxy;

    return 0;
}
```

正常来说Proxy模式的各个类不应该是直接调用new去构造, 而是通过类似工厂方法模式去获取, 以及结合其它设计模式.

### 要点总结

- “**增加一层间接层**”是软件系统中对许多复杂问题的一种常见解决方法。在面向对象系统中，直接使用某些对象会带来很多问题, 作为间接层的poxy对象便是解决这一问题的常用手段。
- 具体proxy设计模式的实现方法、实现粒度都相差很大，有些可能**对单个对象做细粒度的控制**，如copy-on-write技术，有些可能**对组件模块提供抽象代理层**，**在架构层次对对象做proxy**。
- Proxy并不一定要求保持接口完整的一致性, 只要能够实现间接控制，有时候损及一些透明性是可以接受的。

## Adapter

### 动机

- 在软件系统中，由于应用环境的变化，常常需要将“一些现存的对象”放在新的环境中应用，但是新环境要求的接口是这些现存对象所不满足的。
- 如何应对这种“迁移的变化”？如何既能利用现有对象的良好实现，同时又能满足新的应用环境所要求的接口？

### 模式定义

> 将一个类的接口转换成客户希望的另一个接口. Adapter模式使得原本由于接口不兼容而不能一起工作的那些类可以一起工作. ——《设计模式》GoF

### 结构

![[Untitled 897.png]]

Adaptee就是被适配者, 遗留接口, 需要通过Adapter转换. 

### 应用场景

比较典型的就比如插座跟各种插头, 还有STL的stack和queue的实现, 不过stack和queue本身既是接口又是实现, 它们自己就是Target和Adapter, 而它们内部的deque就是Adaptee了, 所以不能太死板. 

```c++
// Adaptee interface
class Plug
{
protected:
	string specification;
public:
	Plug(const string& s) : specification(s) {}
	virtual void spCharge() = 0;
};

// Adaptee 1: Type1 plug
class Type1 : public Plug
{
public:
	Type1(const string& s) : Plug(s) {
	}
	virtual void spCharge() {
		cout << specification << " type 1 is charging..." << endl;
	}
};

// Adaptee 2: Type2 plug
class Type2 : public Plug
{
public:
	Type2(const string& s) : Plug(s) {
	}
	virtual void spCharge() {
		cout << specification << " type 2 is charging..." << endl;
	}
};

// Target interface
class Socket
{
public:
	virtual void charge() = 0;
	virtual void setPlug(Plug* p) = 0;
};

// Adapter class
class Adapter : public Socket
{
private:
	Plug* plug;
public:
	Adapter() {}
	Adapter(Plug* p) : plug(p) {}
	virtual void charge() {
		plug->spCharge();
	}
	virtual void setPlug(Plug* p) {
		plug = p;
	}
};
```

```c++
int main() {
	Plug* p1 = new Type1("A");
	Plug* p2 = new Type2("b");
	Socket* s = new Adapter();
	s->setPlug(p1); 
	s->charge(); // A type 1 is charging...
	s->setPlug(p2);
	s->charge(); // b type 2 is charging...
	delete p1;
	delete p2;
	delete s;
}
```

### 要点总结

- Adapter模式主要应用于"希望复用一些现存的类，但是接口又与复用环境要求不一致的情况”，在遗留代码复用、类库迁移等方面非常有用。
- GoF 23定义了两种Adapter模式的实现结构，：对象适配器和类适配器。但类适配器采用“多继承”的实现方式般不推荐使用。**对象适配器**采用”对象组合“的方武，更符合松耦合精神。
- Adapter模式可以实现的非常灵活，不必拘泥于Gof23中定义的两种结构。例如，完全可以将Adaptert模武中的“现存对象”作为新的接口方法参数，来达到适配的目的。

## Mediator

### 动机

- 在软件构建过程中，经常会出现多个对象互相关联交互的情况, 对象之间常常会维持一种复杂的引用关系，如果遇到一些需求的更改，这种直接的引用关系将面临不断的变化。
- 在这种情况下，我们可使用一个“中介对象”来管理对象间的关联关系，避免相互交互的对象之间的紧耦合引用关系，从而更好地抵御变化。

### 模式定义

> 用一个中介对象来封装(封装变化)一系列的对象交互。中介者使各对象不需要显式的相互引用(编译时依赖→运行时依赖)，从而使其耦合松散（管理变化），而且可以独立地改变它们之间的交互。——《设计模式》GoF

### 结构

![[Untitled 898.png]]

### 应用场景

宗旨是把直接依赖关系转换为间接依赖关系. Facade隔离的是系统内外, Mediator隔离的是系统内的功能( A ↔ B  转换为 A ↔ Mediator ↔ B). 老师也没说具体代码, 只说了个UI设计上的场景. 

![[Untitled 899.png]]

```c++
using namespace std;
class Mediator;

class Component
{
protected:
	Mediator* dialog;
public:
	Component(Mediator* d) : dialog(d) {}
	virtual void click() = 0;
	virtual void keypress() = 0;
	void setMediator(Mediator* m) {
		this->dialog = m;
	}
};

class Mediator
{
public:
	virtual void notify(Component* sender, const string& event) = 0;
};

class Button : public Component
{
public:
	Button (Mediator* d = nullptr) : Component(d){}
	virtual void click() {
		cout << "button click" << endl;
		dialog->notify(this, "click");
	}
	virtual void keypress() {
		cout << "button keypress" << endl;
		dialog->notify(this, "keypress");
	}
};

class Textbox : public Component
{
public:
	Textbox(Mediator* d = nullptr) : Component(d) {}
	virtual void click() {
		cout << "Textbox click" << endl;
		dialog->notify(this, "click");
	}
	virtual void keypress() {
		cout << "Textbox keypress" << endl;
		dialog->notify(this, "keypress");
	}
};

class AuthenticationDialog : public Mediator
{
private:
	Button* btn;
	Textbox* tb;
public:
	AuthenticationDialog(Button* b = nullptr, Textbox* t = nullptr)
		: btn(b), tb(t){
		btn->setMediator(this);
		tb->setMediator(this);
	}
	virtual void notify(Component* sender, const string& event) {
		if (event == "click") {
			cout << "dialog click: " << endl;
			sender->keypress();
		}
		else if (event == "keypress") {
			cout << "dialog keypress: " << endl;
		}
	}
};
```

```c++
int main() {
	Button* btn = new Button();
	Textbox* textbox = new Textbox();
	Mediator* d = new AuthenticationDialog(btn, textbox);
	
	btn->click();
	textbox->keypress();
}
// button click
// dialog click:
// button keypress
// dialog keypress:

// Textbox keypress
// dialog keypress:
```

### 要点总结

- 将多个对象间复杂的关联关系解耦，Mediator模式将多个对象间的控制逻辑进行集中管理，变“多个对象互相关联”为“**多个对象和一个中介者关联**”，简化了系统的维护，抵御了可能的变化。
- 随着控制逻辑的复杂化，Mediator具体对象的实现可能相当复杂。这时候可以对Mediator对象进行分解处理。
- Facade模式是解耦系统间（单向）的对象关联关系；Mediator模式是解耦系统内各个对象之间（双向）的关联关系。

# 状态变化

在组件构建过程中，某些对象的状态经常面临变化，如何对这些变化进行有效的管理？同时又维持高层模块的稳定？“状态变化”模式为这一问题提供了一种解决方案。

## State

### 动机

- 在软件构建过程中，某些对象的状态如果改变，其行为也会随之而发生变化，比如文档处于只读状态，其支持的行为和读写状态支持的行为就可能完全不同。
- 如何在运行时根据对象的状态来透明地更改对象的行为？而不会为对象操作和状态转化之间引入紧耦合？

### 模式定义

> 允许一个对象在其内部状态改变时改变它的行为。从而使对象看起来似乎修改了其行为。
——《设计模式》GoF

### 结构

![[Untitled 900.png]]

### 应用场景

这个很像策略模式。视频讲解的案例是网络状态有Close, Connect, Open等。

```c++
class NetworkState
{
public:
	NetworkState* pNext;
	virtual void operation1() = 0;
	virtual void operation2() = 0;
};

// 用了单例
class ClosedState : public NetworkState
{
private:
	static NetworkState* m_instance;
public:
	static NetworkState* getInstance() {
		if (m_instance == nullptr) {
			m_instance = new ClosedState();
		}
		return m_instance;
	}
	virtual void operation1() {
		cout << "ClosedState 1" << endl;
		pNext = this;
	}
	virtual void operation2() {
		cout << "ClosedState 2" << endl;
	}
};

class AwaitState : public NetworkState
{
private:
	static NetworkState* m_instance;
public:
	static NetworkState* getInstance() {
		if (m_instance == nullptr) {
			m_instance = new AwaitState();
		}
		return m_instance;
	}
	virtual void operation1() {
		cout << "AwaitState 1" << endl;
		pNext = ClosedState::getInstance();
	}
	virtual void operation2() {
		cout << "AwaitState 2" << endl;
	}
};

class OpenState : public NetworkState
{
private: 
	static NetworkState* m_instance;
public:
	static NetworkState* getInstance() {
		if (m_instance == nullptr) {
			m_instance = new OpenState();
		}
		return m_instance;
	}
	virtual void operation1() {
		cout << "open state 1" << endl;
		pNext = AwaitState::getInstance();
	}
	virtual void operation2() {
		cout << "open state 2" << endl;
	}
};
```

```c++
class NetworkProcessor
{
private:
	NetworkState* state;
public:
	NetworkProcessor(NetworkState* s = nullptr) : state(s){
	}
	void setState(NetworkState* s) {
		state = s;
	}

	void operation1() {
		state->operation1();
		state = state->pNext == nullptr ? state : state->pNext;
	}
	void operation2() {
		state->operation2();
		state = state->pNext == nullptr ? state : state->pNext;
	}

};

// 下面是必须的，不然vs2022会报LNK2001错误
NetworkState* OpenState::m_instance = nullptr;
NetworkState* AwaitState::m_instance = nullptr;
NetworkState* ClosedState::m_instance = nullptr;
```

```c++
int main() {
	NetworkState* open = OpenState::getInstance();
	NetworkProcessor* np = new NetworkProcessor(open);

	np->operation1(); // open state 1
	np->operation2(); // AwaitState 2
	np->operation1(); // AwaitState 1
	np->operation1(); // ClosedState 1
}
```

### 要点总结

- State模式将所有与一个特定状态相关的行为都放入一个State的子类对象中，在对象状态切换时，切换相应的对象; 但同时维持State的接口，这样实现了具体操作与状态转换之间的解耦。
- 为不同的状态引入不同的对象使得状态转换变得更加明确，而目可以保证不会出现状态不一致的情况，因为转换是原子性的——即要么彻底转换过来，要么不转换。
- 如果State对象没有实例变量，那么各个上下文可以共享同一个State对象，从而节省对象开销

## Memento

### 动机

- 在软件构建过程中，某些对象的状态在转换过程中，可能由于某种需要要求程序能够**回溯到对象之前处于某个点时的状态**。如果使用一些公有接口来让其他对象得到对象的状态，便会暴露对象的细节实现。
- 如何实现对象状态的良好保存与恢复，但同时又不会因此而破坏对象本身的封装性？

### 模式定义

> 在不破坏封装性的前提下，捕获一个对象的内部状态，并在该对象之外保存这个状态。这样以后就可以将该对象恢复到原先保存的状态。
——《设计模式》GoF

### 应用场景

应该是唯一一章不算是伪代码的章节。备忘录的实现有很多，比较典型的我想到的有游戏存档、git等。以今天来看，下面示例代码的备忘录实现是很低效过时了，主要是要理解备忘录的思想。

```c++
class Memento
{
    string state;
    //..
public:
    Memento(const string& s) : state(s) {}
    string getState() const { return state; }
    void setState(const string& s) { state = s; }
};

class Originator
{
    string state;
    //....
public:
    Originator() {}
    Memento createMomento() {
        Memento m(state);
        return m;
    }
    void setMomento(const Memento& m) {
        state = m.getState();
    }
};
```

```c++
int main()
{
    Originator orginator;

    //捕获对象状态，存储到备忘录
    Memento mem = orginator.createMomento();

    //... 改变orginator状态
    //从备忘录中恢复
    orginator.setMomento(mem);

}
```

### 要点总结

- 备忘录(Memento)存储原发器(Originator)对象的内部状态，在需要时恢复原发器状态。
- Memento模式的核心是**信息隐藏,** 即Originator需要向外接隐藏信息，保持其封装性。但同时又需要将状态保持到外界(Memento)。
- 由于现代语言运行时（如C#、Java等）都具有相当的对象序列化支持，因此往往采用效率较高、又较容易正确实现的**序列化方案**来实现Memento模式。
